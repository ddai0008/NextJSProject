## The mechanism: what runs where

```
 Windows ── Docker Desktop (a Linux VM)
                └── container "postgres" ◄── volume "pgdata" (the database files live here)
                         ▲ published on 127.0.0.1:55432
 WSL (this terminal) ────┘
   ├── your app            node + Next.js        (npm run dev / next start)
   ├── the migration tool  drizzle-kit
   ├── the seed script     node scripts/seed.mjs
   └── the tests           npm run act
```

- A **container** is disposable; a **volume** is not. The container can be deleted and re-created, and the data stays as long as
  the volume does. *Where* inside the container the volume is mounted must be where the image actually keeps its data. Images
  change that between major versions.
- **Two database roles, on purpose.** The container is created with a superuser, `postgres`. `npm run db:up` then makes sure the role you will really use exists: `crm`, which owns the database `crm`, runs the migrations and the seed, and is **not** a superuser (it can create databases and roles, like the administrator of a managed Postgres). The tooling uses `postgres` only for the few steps that need it (creating `crm`, installing the statistics extension the tests read). Why bother? A superuser is exempt from rules that a real owner is not (A09 is about one of them), so a test that passes as a superuser can fail in production.
- **Migrations.** `db/schema/*.ts` is the state you *want*. `npm run db:generate` compares it with the last snapshot in
  `db/migrations/meta` and writes a SQL file; `npm run db:migrate` runs the SQL files that have not run yet and records them in the
  table `drizzle.__drizzle_migrations`. The SQL is committed to git: it is the history of your schema.
- **The seed** reads `scripts/lib/seed.mjs`, which uses a fixed random seed, so the same command produces the same names,
  emails and dates every time. (Ids are generated by the database and differ.) Tests can therefore assert on counts and content.
- **Build time versus request time.** `next build` runs your code to find out what it can prerender. A Route Handler that reads the
  database for every request is *dynamic*: its answer is not baked into the build (the build output marks it `ƒ`), and it answers when a
  request arrives. Note that Next.js may still *try* the handler while building to find that out: with no database that attempt fails, and
  if your handler logs the failure you will see your own log line in the build output. The activity runner builds your app **with no
  database reachable, on purpose**: a build that needs a database is a bug, because builds run in CI and in Docker where there is none.
- **The runner.** `npm run act -- 1` checks Node and Docker, starts Postgres, builds a *test database* (your migrations + a small
  seed, cached until a migration changes), gives this run its own copy, builds and starts your app, runs the tests in
  `tests/activities/01-boot/`, then cleans everything up.

## Requirements

1. **Postgres runs.** `npm run db:up` must leave a healthy Postgres 18 container with its data on a named volume. If it does not
   start, find out why from the container itself, not from guessing.
2. **The schema is in the database.** Generate the first migration from the schema in `db/schema/` and apply it to the development
   database `crm`. Commit the generated files in `db/migrations/`.
3. **The data is loaded.** Run the full seed. Then look at it with `npm run psql` (it opens `psql` inside the container): list the
   tables, count the contacts, see the organisations.
4. **`GET /api/health`.** Create `app/api/health/route.ts`:
   - Healthy: status **200**, JSON `{ "status": "ok", "database": "up", "serverVersion": <string>, "checkedAt": <ISO timestamp> }`.
     `serverVersion` is what the *database server* reports, not a constant.
   - The database cannot be reached: status **503**, JSON `{ "status": "error", "database": "down", "checkedAt": <ISO timestamp> }`.
   - The body never contains a connection string, an error message or a stack trace. Log the details on the server instead.
   - The monitor must never receive a stale answer.
5. **Chromium starts.** Browser tests begin in A04. Install what Playwright needs now so that does not surprise you later.

## Acceptance criteria

Run `npm run act -- 1`. Each line is one test; the first failure is usually the cause of the rest.

| Test | What it checks |
| --- | --- |
| A01.1 | Chromium can start. |
| A01.2 | Postgres 18 runs from `compose.yaml` and its data directory is on a **named volume** mounted where the image keeps its data. |
| A01.3 | A migration exists and the development database has the tables `orgs`, `users`, `companies`, `contacts`. |
| A01.4 | The development database holds 10,000+ contacts across 4 organisations. |
| A01.5 | Seeding twice gives identical content (names, emails, dates). |
| A01.6 | `GET /api/health` answers 200 with the JSON above. |
| A01.7 | The answer is computed per request: `checkedAt` changes between two requests 1.2 s apart. |
| A01.8 | With an unreachable database the endpoint answers 503 and `"database": "down"`, with nothing sensitive in the body. |

## Messages you may meet

- A container that exits at once. `docker compose ps -a` shows `Exited (1)`; `docker compose logs postgres` has the reason. For this
  starter it begins: `Error: in 18+, these Docker images are configured to store database data in a format which is compatible with "pg_ctlcluster"`.
- Chromium downloaded but will not run: `error while loading shared libraries: libnspr4.so: cannot open shared object file`.
  It needs system libraries once (ask a hint, or read the Playwright "browsers" page below).
- Nothing listens where you connect: `connect ECONNREFUSED 127.0.0.1:55432`.

## Stretch goals

- Stop the container with `docker compose down` and start it again with `npm run db:up`. Is your data still there? Now try
  `docker compose down -v`. What is different, and why does the second one exist? (If `npm run db:up` ever tells you that the volume was created by an older `compose.yaml`, this is the command it means.)
- Hit `/api/health` a few times, then in `npm run psql` run `select calls, query from pg_stat_statements order by calls desc limit 5;`.
  What did your handler cost the database per request?
- Make the health check give up on a database that answers too slowly (not just one that refuses). Where would the timeout live?

## Self-review checklist

- [ ] I can explain why the container exited and what the Postgres image changed between major versions.
- [ ] If the database accepts the connection but never answers, what does the monitor see? (Look at `db/client.ts`.)
- [ ] My migration files are committed (`db/migrations/*.sql` **and** `db/migrations/meta/`).
- [ ] I know why `next build` must pass with the database stopped.
- [ ] Before running the tests I wrote down how many I expected to pass. (Calibration: it is the skill the diagnostic showed you need.)
